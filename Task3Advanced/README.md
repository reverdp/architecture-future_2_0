## Оценка рисков внедрения

Трансформация компании "Будущее 2.0" связана с переходом от устаревшего DWH, PowerBuilder, кастомной BI и интеграций через Apache Camel к облачной доменной архитектуре, порталу самообслуживания данных и событийной платформе.

### Карта рисков трансформации
| №  | Категория риска     | Риск                                                                          | Вероятность | Влияние на бизнес |
|----|---------------------|-------------------------------------------------------------------------------| ----------- | ----------------- |
| 1  | Архитектурный       | Неверное выделение границ доменов                                             | Средняя     | Высокое           |
| 2  | Архитектурный       | Сохранение DWH как центра бизнес-логики                                       | Высокая     | Высокое           |
| 3  | Архитектурный       | Сильная связанность доменов через синхронные интеграции                       | Высокая     | Высокое           |
| 4  | Архитектурный       | Слишком быстрый отказ от легаси систем                                        | Средняя     | Высокое           |
| 5  | Технологический     | Сложность миграции с SQL Server 2008                                          | Высокая     | Высокое           |
| 6  | Технологический     | Потеря или искажение данных при миграции                                      | Средняя     | Высокое           |
| 7  | Технологический     | Низкая производительность новой витрины данных                                | Средняя     | Высокое           |

### План управления рисками
| Риск                                             | Меры снижения                                                                                                  | Тип мер                      |
|--------------------------------------------------|----------------------------------------------------------------------------------------------------------------| ---------------------------- |
| Неверное выделение границ доменов                | Провести domain discovery, event storming, описать bounded contexts и ответственность доменов                  | Управленческие               |
| Сохранение DWH как центра бизнес-логики          | Постепенно выносить бизнес-логику в доменные сервисы, DWH оставить как временный источник и мост совместимости | Технические                  |
| Сильная связанность через синхронные интеграции  | Переходить к событийному обмену, использовать брокер сообщений, outbox, ретраи и DLQ                           | Технические                  |
| Слишком быстрый отказ от легаси-систем           | Использовать поэтапную миграцию, strangler pattern и параллельную работу старого и нового контуров             | Управленческие               |
| Сложность миграции с SQL Server 2008             | Мигрировать данные поэтапно                                                                                    | Технические                  |
| Потеря или искажение данных                      | Использовать контрольные суммы, миграционные тесты и параллельное сравнение отчётов                            | Технические                  |
| Низкая производительность витрины данных         | Использовать кэширование, предагрегации, лимиты на тяжёлые запросы                                             | Технические                  |
| Ошибки в обработке событий, очередях и DLQ       | Настроить мониторинг очередей, алерты, правила повторной обработки и регламент разбора DLQ                     | Технические                  |
| Недостаточная наблюдаемость новой платформы      | Внедрить централизованные логи, метрики, трассировку                                                           | Технические                  |
| Утечка медицинских или финансовых данных         | Применить шифрование, маскирование, токенизацию, аудит доступа, DLP                                            | Технические                  |
| Ошибки разграничения доступа                     | Внедрить RBAC/ABAC, регулярный пересмотр прав                                                                  | Технические                  |
| Попадание медицинских данных в витрину           | Ввести классификацию данных, policy engine и автоматические проверки перед загрузкой в аналитику               | Технические + управленческие |
| Несоблюдение требований регуляторов              | Определить правила хранения и обработки медицинских и финансовых данных                                        | Управленческие + технические |
| Недостаток компетенций                           | Организовать обучение команд, привлечь экспертов                                                               | Управленческие               |
| Сопротивление пользователей                      | Провести обучение, пилотные запуски                                                                            | Управленческие               |
